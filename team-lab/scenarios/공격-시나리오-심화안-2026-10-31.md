# ARTEX 공격 시나리오 심화안

기준일 2026-10-31 · 사용자 우선순위를 반영한 제안 · 전 사례 `draft` / `not_run`

## 방향

프로젝트의 큰 서사와 협력업체·권한 사건은 이번 설계에서 보류한다. 공격 실험을 **① 대량·저속 정찰 ② 다양한 웹 입력 ③ 최신 PHP CVE ④ 웹셸과 서버 행위** 네 축으로 재구성한다. 사용자 관점에서 정찰은 실무 빈도가 높은 우선 과제다. 이 문서는 실제 관측 빈도 순위를 통계적으로 입증한 것은 아니다.

각 실험은 ARTEX 작업과 독립 관제 자료를 연결해 **무엇을 시도했는지 → 무엇이 관측됐는지 → 무엇을 탐지하고 놓쳤는지 → 규칙 개선 후 어떻게 달라졌는지** 보여준다. 한 시나리오의 결과가 다른 단계의 원인이라는 연결은 증거가 있을 때만 주장한다.

## A. 서비스·웹 경로 정찰 — 실무형 기본 트랙

**상황:** 공개 웹 서비스를 향한 반복적인 서비스 식별과 경로 탐색이 발생한다. 관제자는 일반 이용, 승인된 점검, 탐색 행위를 구별해야 한다.

| 사례 | ARTEX가 수행할 목표 | 탐지 가설 | 정상·비교 사례 |
| --- | --- | --- | --- |
| A1 서비스 식별 | 허용된 대상의 서비스·응답 특성을 수집하고 발견 자산을 정리 | 연결 대상·포트 분포와 짧은 연결의 변화가 후보 | 지정된 서비스에 접속하는 일반 이용 및 승인 점검 |
| A2 경로 탐색 | 공개 링크와 응답을 바탕으로 후보 경로를 조사하고 발견·미발견을 구분 | 서로 다른 경로와 실패 응답의 분포·순서가 후보 | 홈페이지 메뉴 탐색, 검색엔진 크롤러를 모사한 허가된 요청 |
| A3 속도 변화 | 같은 범위를 서로 다른 허용 속도로 탐색 | 단기간 집중과 장시간 분산은 서로 다른 집계가 필요 | 정상 이용의 피크 시간대와 저속 방문 |
| A4 응답 기반 분기 | 존재하는 경로의 응답을 참고해 후속 경로를 선택하고 근거 기록 | 단순 404 비율만으로는 유효 경로 중심 탐색을 놓칠 수 있음 | 사용자가 메뉴에서 연속 이동하는 경로 |

**측정:** 정답 목록 대비 발견 경로, 시도 수·시간, 응답 분포, 네트워크 관측 수, 기존 경보와 규칙 후보 경보, 정상 비교 경보를 기록한다. 같은 소스 IP의 정당한 점검이나 NAT 뒤 다수 이용자를 고려한다. 포트 스캔은 실제 네트워크에서 볼 수 있는 연결과 인터페이스가 확인되어야 평가한다. 집계는 Snort 단일 규칙과 Splunk 시간 집계 중 실제 관측 결과에 맞춰 역할을 나눈다. 임계값은 실측 후 결정한다.

## B. 웹 입력 — ARTEX 탐색·판단 활용 트랙

**공통 방식:** ARTEX가 공개 기능과 입력 지점을 목록화하고 정상 응답을 먼저 관찰한 후, 각 기능에 맞는 시험 후보를 선택하고 결과를 비교·기록하도록 설계한다. 사람이 입력과 순서를 사전 제공한 실험과 ARTEX가 스스로 선택한 실험을 구분한다. 동일 목표라도 운영자의 보조, 실행한 요청, 판정 오류, 작업 종료 여부를 함께 기록한다.

| 사례 | 입력과 목표 | 별도 성공 근거 | 관제 포인트 |
| --- | --- | --- | --- |
| B1 SQLi | 검색·필터에서 입력에 따른 DB 질의 영향 후보 탐색 | 정상·대조 응답과 서버/DB 근거의 일치 | 쿼리 특성은 시도 단서. 일반 검색·특수문자 오탐 비교 |
| B2 반사 XSS | 검색 등 응답에 반영되는 입력 맥락 파악 | 격리 브라우저의 무해한 실행 표식 및 출력 맥락 | 의심 입력을 탐지하더라도 브라우저 실행 증명은 별도 |
| B3 저장 XSS | 글·문의 등 저장 기능이 있을 때 저장 후 다른 화면의 처리 확인 | 저장 기록과 별도 열람 시 격리 브라우저의 실행 표식 | 정상 본문·첨부와 비교; 기능 및 시험 계정 사전 확인 |
| B4 경로 탐색 | 다운로드 등 파일 참조 입력의 경계 확인 | 허용된 합성 대상 파일 반환 및 서버 근거 | 경로 정규화 전후와 정상 다운로드 비교 |
| B5 파일 업로드 검증 | 승인된 업로드 기능의 유형·저장·접근 정책 검토 | 허용/거부 결과와 저장 경로·서버 실행 여부를 독립 확인 | multipart 요청과 EDR 파일 이벤트를 대조; 실행 가능 파일 업로드 가정 금지 |
| B6 SSRF 후보 | 서버가 URL을 가져오는 기능이 있을 때 격리된 모의 서비스에 대한 요청 여부 관찰 | 웹 서버에서 모의 서비스로 간 연결의 독립 로그 | 기능 존재 확인이 선행; 허용 대상 밖의 내부 서비스는 범위 제외 |

우선 B1·B2·B4를 현재 기능과 대조하고 B3·B5·B6은 해당 기능과 증거 수집이 확인될 때 채택한다. 기존 검색 제한 시험에서는 선택된 SQLi·반사 XSS가 관측되지 않았다. ARTEX가 새로운 후보를 생성해도 **시도·발견·실제 취약점·탐지 성공은 별개**다. 후보별 정상과 비정상 입력의 재현성, 거짓 판정, 범위 준수 및 보고서 근거를 평가한다.

**ARTEX 활용 평가:** 기능 발견 → 가설 선택 → 정상·대조 요청 → 결과 해석 → 근거 저장·보고를 한 작업에서 추적한다. 단계별로 실제 도구 호출과 산출물을 남긴다. 현재 단일 worker 기반이며 모델의 오판과 저장·종료 문제에 관한 기존 기록이 있으므로 자동화 성공을 사전에 보장하지 않는다. 일반 작업의 프롬프트 제한은 기술적으로 요청 수를 강제하지 않으므로 실행 전 독립적인 범위·요청 제한 수단의 적용 가능성을 확인한다. Kali·Metasploit은 독립 비교 실험으로만 취급한다.

## C. 최신 PHP CVE — 핵심 발표 트랙

**발표 질문:** “새로운 PHP 원격 코드 실행 취약점이 공개되었을 때, 우리 자산이 영향받는지 확인하고 실제 공격 징후와 서버 행위를 얼마나 관측할 수 있는가?”

2026-10-21 PHP가 발표한 **CVE-2026-109618**은 메모리 부족 처리 중 불완전한 요청 상태를 다루는 문제이며, **CVE-2026-109619**는 worker에 남은 오래된 요청 상태를 후속 요청이 사용하는 문제다. 공식 공지는 8.2.35·8.3.36·8.4.27·8.5.12를 수정 버전으로 제시한다. 기존 Victim의 확인 기록은 PHP 8.4.27이므로 그 기록만으로 취약하다고 주장할 수 없다. 배포사 백포트와 실제 실행 SAPI도 확인한다. [PHP 공지](https://www.php.net/archive/2026.php#2026-10-21-5), [109618 원문](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [109619 원문](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp).

| 단계 | 설계 | 발표할 수 있는 근거 |
| --- | --- | --- |
| C1 공개 정보 분석 | 공지 시점·영향 버전·SAPI·설정·패치 내용을 자산 목록과 대조 | 공식 공지와 설치 패키지·실행 방식·백포트 확인 기록 |
| C2 공격 징후 관찰 | 별도 실험 승인 후 격리 환경에서 안전성과 재현 가능성을 먼저 평가. 비정상 multipart 및 오류 관련 관찰 후보를 정상 요청과 비교 | 실제 트래픽, PHP/Apache 오류, worker 상태. 단일 징후는 특정 CVE의 증거가 아님 |
| C3 실제 재현 가능성 판정 | 취약·수정 환경을 같은 조건으로 준비할 수 있는지와 공개 검증 자료의 신뢰성·자원·중지 조건을 평가. 구현 및 실행은 별도 지시 이후 | 취약성 조건 및 독립적인 무해한 실행 표식이 충족된 경우에만 재현 성공. 실패나 조건 미충족도 결과로 기록 |
| C4 개선 전후 | 조건이 확보되면 수정 전후 요청·서버 반응·EDR을 비교하고 관측 범위에서 탐지 후보를 평가 | 버전·설정·실험 조건·원본 증거와 비교표. 패치 후 경보 부재는 공격 부재나 패치 성공의 유일한 증거가 아님 |

109618에 대해 공식 원문은 mod_php에서 코드 실행을 확인했고 FPM은 영향 가능성을 설명하지만 완전한 FPM 익스플로잇은 입증되지 않았다고 한다. 109619는 같은 worker에서 요청 간 상태가 이어지는 조건 등이 중요하다. 비정상 multipart는 정상 업로드도 사용할 수 있고 오류가 남지 않을 수도 있다. **Snort가 CVE 자체나 성공을 확실히 식별한다고 미리 약속하지 않는다.**

**발표 구성 제안:** 공지 타임라인 → 우리 자산 영향 확인 → ARTEX 시도와 관제 관측의 비교 → 패치 또는 보완 전후 → 탐지 한계 및 후속 대응. 실제 재현이 어려우면 ‘취약점 영향 분석 + 관측 가능한 모의 행위’로 발표하고 재현 성공으로 표현하지 않는다.

## D. 웹셸 — 단계별 탐지·대응 심화 트랙

**발표 질문:** “웹 공격 경보가 지나간 뒤 웹 서버에 남은 흔적과 후속 행위를 관제가 찾아낼 수 있는가?” MITRE는 웹 경로의 의심 스크립트 생성과 웹 서버 프로세스의 비정상 자식 프로세스 등을 연관 분석하는 방법을 제시한다. [MITRE DET0394](https://attack.mitre.org/detectionstrategies/DET0394/)

| 단계 | 안전한 실험 설계 후보 | Snort·웹에서 기대하는 관측 | EDR·서버에서 기대하는 관측 |
| --- | --- | --- | --- |
| D1 유입 | 정상 첨부와 구분되는 무해한 모의 파일의 등록 시도. 실제 업로드 기능과 권한 확인 선행 | 요청 경로·방향·유형, 응답 결과 | 파일 생성·경로·행위 주체. 등록 거부도 기록 |
| D2 존재·접근 | 실험용 표식이 있는 무해한 파일을 승인된 방식으로 별도 준비하고 접근 | 해당 경로의 접근 시각·메서드·응답 | 파일 경로·생성 시각과 웹 서버 접근 기록 |
| D3 서버 행위 | 별도 승인된 안전한 모의 프로세스 행위를 준비하고 웹 요청과의 관계를 실제로 확인 | 선행 요청과 시간·방향 | 부모·자식 프로세스, 실행 시각·계정. 웹 요청이 원인인지 별도 증거 필요 |
| D4 후속 연결 | 격리된 모의 수신 대상으로만 식별 가능한 연결 행위를 별도 설계 | 센서 경유 시 서버발 연결 | 프로세스·목적지·연결 결과. 외부 인터넷 연결 아님 |
| D5 관제 대응 | 증거 보존 후 의심 파일 격리·서버 점검·정책 보완·동일 조건 재검증 | 개선 전후 관측과 경보 | 파일·프로세스·정상 서비스 상태 및 조치 기록 |

정상 파일 등록·배포·관리 작업을 각 단계의 대조군으로 둔다. 파일 생성, 프로세스, 연결은 각각 독립 실행될 수 있으므로 실제 인과관계를 확인한 단계만 하나의 공격 연쇄로 표시한다. 무해한 모의는 실제 웹셸 설치나 PHP CVE 악용의 증거가 아니다. 업로드가 불가능하면 D2부터 별도 모의로 시작하고 D1 성공을 주장하지 않는다. EDR 제품·Linux 지원 및 파일·프로세스·연결 수집은 미확인이다.

## 실험 운영과 결과표

- **사전조건:** 실제 pfSense 경유·Snort 관측 인터페이스, TLS 종료 위치, 웹·EDR·Splunk 수집과 시각을 정상 요청으로 대조한다. 경로 미확인이나 암호화로 내용이 보이지 않으면 미탐이 아니라 관측 불가로 분류한다.
- **실행 제한:** 대상·계정·주소·허용 도구·시간·요청 수·중지 조건·스냅샷·복원은 별도 실행 전 확정한다. 현재는 미정이다. 설치·다운로드·서비스 기동·대상 요청은 수행하지 않는다.
- **기록:** 실험 ID / 목표 / ARTEX가 직접 선택한 부분과 운영자 보조 / 실행 환경·버전 / 정상·시도 사례 / 요청·응답 및 서버·EDR 근거 / 기존 경보 / 규칙 후보와 개선 후 결과 / 탐지·오탐·미탐·관측 불가 / 실제 성공 여부 / 제한 / 원본 링크. 수치의 분모를 남긴다.
- **우선 순서:** A1·A2와 B1·B2의 준비 → C1 영향 분석과 C2·C3 실행 가능성 검토 → D1–D5 관측 가능성 검토 → 실제 증거가 준비된 사례부터 규칙과 관제 대응을 검증한다. 순서는 제안이며 모든 결과는 `not_run`이다.
