# ARTEX 팀 실험 준비

기준일: 2026-10-29 · 현재 단계: 로컬 정상 GET 및 공개 페이지 8GET 기초 점검·로그 대조 / 원래 진단은 timeout, 후속 저장·종결 보완 코드 회귀 검사 통과 / 실습망·관제 연계 미검증

매일 켜고 끄는 방법은 [ARTEX Mac 실행·종료 가이드](docs/ARTEX-Mac-실행-종료-가이드.md)를 따른다. 실행·정지 명령, Docker 화면의 버튼 사용법, Ollama 종료와 상태 확인 방법을 정리했다.

팀 조직의 [SSLC-FiveEyes/artex-global](https://github.com/SSLC-FiveEyes/artex-global)을 Mac으로 가져와 설정 예시·시나리오·기록 양식을 준비했다. 이후 사용자 요청으로 Ollama 0.32.5를 설치하고 `qwen3.5:9b-q4_K_M`을 다운로드해 단독 기본 응답과 도구 호출을 확인했다. 이후 ARM64 릴리스 이미지를 고정해 Docker의 ARTEX·PostgreSQL을 기동하고 Qwen 32K 프로파일 연결을 확인했다. 10/29에는 실제 작업의 planner·worker가 로컬 홈페이지에 정상 GET 1회를 보내고 서버 로그에 남긴 것을 확인했다. 최초 설치에서는 소스를 빌드하지 않았으며, 이후 저장·종결 보완은 같은 릴리스 소스에 제한된 변경을 적용해 별도 로컬 이미지로 빌드했다.

첫 단독 시험의 native API는 32K 문맥 할당, OpenAI 호환 도구 왕복은 기본 4K에서 확인했다. 이때 시스템 스왑이 0에서 약 2.1GB로 증가했다. [첫 실측 기록](results/2026-10-27-qwen35-9b-q4km-local-smoke.json)은 당시 조건의 기록으로 보존한다.

후속 사용자 요청으로 `artex-qwen35-9b-q4km-32k` 별칭을 등록하고, 같은 별칭의 OpenAI 호환 API에서 한국어 단문과 계산 도구 왕복 후 실제 문맥 32768·GPU 실행을 확인했다. 이 시험의 시스템 스왑은 시작 2040.12M에서 종료 2821.00M으로 증가했다. 모델만의 메모리·피크를 분리한 값은 아니며, 이 모델 단독 시험 시점에는 32K 길이의 장문 처리·ARTEX 연동·Docker 동시 실행이 미검증이었다. 이후의 기본 연결 검증은 아래 실제 배포 구성과 별도 기록을 따른다. 시험 완료 시 모델은 로드 상태였고 유휴 자동 해제 시각을 기록했다. [32K 별칭 실측 기록](results/2026-10-27-qwen35-32k-alias-smoke.json)도 Git 제외 경로에 보관한다.

## 현재 준비 상태

- 조직 포크를 로컬 저장소로 복사했다. 기준 커밋은 `fdfb7a17b7da5e2de716c0e98475ec77a41c64c6`다.
- 기존 ARTEX 애플리케이션 소스, 루트 Compose와 upstream 설정 예시는 보존했다.
- 기존 예시는 보존했다. Qwen3.5 9B용 실사용 파일에 로컬 Compose를 추가했고, ARTEX 환경·모델 프로파일·작업 1개/worker 1개 설정을 적용했다. Ollama 전역 환경 파일은 아직 적용하지 않았다.
- 루트 `.env`·`config.json`은 만들지 않았다. 실행 데이터는 `artex-team_appdata`·`artex-team_pgdata` Docker 볼륨에, 실험 원본과 요약은 Git 제외 `evidence/`·`results/`에 보관한다. 로컬 DB 비밀번호는 Git·Docker에서 제외한 `config/artex.mac.env`에만 보관한다. Ollama 모델 파일은 저장소 밖의 로컬 모델 저장소에 보관한다.
- 새 파일과 제외 규칙 변경은 로컬의 미커밋 상태다. GitHub에는 푸시하지 않았다.

## 실제 배포 구성

현재 실행 이미지는 `artex-local:completion-20261029-r3`이며, 아래 최초 릴리스를 기반으로 저장·종결 코드를 보완했다. 상세 변경과 검증·복원은 아래 보완 항목을 따른다.

- Mac 네이티브 Ollama는 유지하고, Docker의 `artex-team-artex-1`에서 `http://host.docker.internal:11434/v1`로 연결한다. Ollama 수신 주소를 외부 공개로 바꾸지 않고 컨테이너 도달을 확인했다.
- 최초 고정 배포는 `v0.3.15-global.1`, 소스 `d6964594a0221cd921b85056d604bce9d8ce54df`의 ARM64 이미지 digest를 고정했다. 로컬 작업 소스 HEAD와는 다르며 로컬 빌드로 기록하지 않는다.
- 로컬 skills 바인드를 사용하지 않고 이미지의 번들 skills 21개가 릴리스 소스와 일치하는지 확인했다.
- `config/compose.mac.local.yaml`로 별도 프로젝트 `artex-team`을 실행한다. 관리 UI와 기록 프록시는 Mac의 `127.0.0.1:8787`, `127.0.0.1:8788`에만 게시하고 DB 포트는 게시하지 않는다.
- ARTEX의 활성 모델은 `artex-qwen35-9b-q4km-32k-tools`, 문맥 32K·스트리밍·`reasoning_effort=low`·출력 한도 4096이다. 작업 1개·worker 1개, 모델 자동 전환과 웹 검색·외부 알림 비활성화를 확인했다.
- 초기 연결 시험에서는 ARTEX 자체 스트리밍 연결 시험의 `OK`와 컨테이너의 비스트리밍 계산 도구 왕복, 실제 문맥 32768·GPU 실행을 확인했다. 이후 실제 worker의 정상 요청 검증은 아래 10/29 후속 기록을 따른다.
- Docker 구축 후 모델 시험 전후 시스템 스왑은 `3800.69M → 6641.75M`이었다. 단계별 시스템 관측값이며 모델만의 최대 사용량이 아니다. 장문·장시간·브라우저 도구 부하는 아직 미검증이다.

접속은 `http://127.0.0.1:8787`, 사용자 이름은 `ARTEX`다. 비밀번호는 Git·Docker 제외 파일인 `.secrets/artex-login.txt`에만 보관한다. 서버 출력 언어는 한국어로 설정했으며, 브라우저 UI는 시스템 설정의 표시 언어에서 한국어를 선택한다.

### 시스템 도구 한국어 설명 적용 · 2026-10-27

사용자가 시스템 도구의 중국어 안내 문제를 제기해, 현재 실행 DB의 시스템 도구 설명 51개와 중첩 항목을 포함한 파라미터 안내 200개를 한국어로 변경했다. 편집창에 남아 있던 기본 에이전트의 중국어 표시 이름 6개도 기존 한국어 메시지와 맞췄다. 원본을 Git 제외 경로에 백업하고, 적용 직전 값 일치 확인과 적용 후 전체 대조를 수행했다. 도구 키·파라미터 구조·필수 여부·열거값·기본값·에이전트 연결·활성화와 내부 추론 프롬프트는 보존했다. 실제 카드와 편집창의 한국어 표시를 확인했다.

도구 설명 필드는 모델에도 전달되므로 이번 변경은 화면에만 적용되는 번역이 아니다. 번역 후 모델 성능은 평가하지 않았으며, 도구 실행·대상 요청·서비스 재시작·설치·빌드는 수행하지 않았다. 도구의 **기본값 복원**이나 향후 스키마 갱신은 중국어 기본 설명을 다시 가져올 수 있다. 공유용 번역 예시는 `config/system-tools.ko.example.json`이며, 명령·검색 예시의 리터럴은 원문을 보존했다.

로컬 소스의 두 도구 편집창에도 기존 `useAgentLabels`를 연결해 표시 언어별 에이전트 이름을 사용하도록 수정했다. 이 소스 변경은 아직 빌드·배포하지 않았고, 현재 앱의 표시는 위 DB 변경으로 반영했다. [적용·보존 검증 기록](results/2026-10-27-system-tools-korean-localization.json)과 [한국어 편집창 캡처](evidence/2026-10-27-system-tools-ko-editor.png)를 로컬에 보관한다.

### 로컬 홈페이지 정상 접속 작업 · 2026-10-29

사용자 실행 요청으로 작업 #1을 생성해 실제 목표 분해·planner·worker·결과 기록·목표 달성을 확인했다. `host.docker.internal:8088`의 홈페이지 첫 화면에 고유 query·User-Agent를 붙인 GET 1회를 보냈고, 도구 출력과 Apache 접속 로그 모두 HTTP 200이었다. 서버가 관측한 출발지는 `172.19.0.1`이며 Docker 경유 주소다. 작업은 10:46:44–10:53:02 KST, 총 6분 18초였고 curl 요청 자체는 0.016초였다. 최종 목표 1/1 `met`, 작업 `done`, 실행 중 worker·모델 호출 0을 확인했다.

기능 성공과 지시 준수 품질을 구분한다. 모델이 고정 RUN_ID 출력을 지원하지 않는 `%{run_id}`로 바꿔 경고를 남겼고, 일부 제약의 allow/deny 분류와 목표의 기록 조건을 잘못 가공했다. planner는 즉시 완료 도구를 호출하지 못하고 300초 마감 정리에서 실제 `prove_goal`을 호출해 완료했다. 모델 호출은 13회였으며, 요청·응답과 서버 로그 대조 성공을 복잡한 자율 실행 적합성으로 확대하지 않는다. 시스템 스왑은 시험 전 4,887.56MiB에서 후 12,293.44MiB로 관측됐으며 다른 앱을 포함한 시스템 값이고 모델 단독 사용량·피크가 아니다.

[실측 JSON](results/local-normal-20261029-104644-64aca5.json)과 [실행 요약](results/local-normal-20261029-104644-64aca5-summary.md)은 Git 제외 로컬 기록이다. 추가 HTTP 재시험·홈페이지 코드/DB 설정 변경은 하지 않았으며 실습 VM·pfSense·Snort·Splunk·공격/탐지/차단은 미검증이다.

### 로컬 공개 페이지 기초 진단 · 2026-10-29

사용자 진단 요청으로 작업 #2에서 고정 공개 주소 8곳의 응답을 수집했다. 운영자가 준비한 수집기를 실제 worker가 한 번 실행했으며, 공개 PHP 화면 6곳은 HTTP 200, robots와 고유 없는 경로 2곳은 404였다. 고유 표식의 Apache GET 8건과 각 응답을 대조했다. 응답 수집은 7.301초였고, 여섯 PHP 응답의 CSP·nosniff·Referrer-Policy·세션 쿠키 속성 및 로그인 csrf 필드를 관측했다. 404의 공통 보안 헤더·요청 추적 ID 불일치는 보완 후보이며, 이번 제한 범위에서 악용 가능한 취약점을 확정하지 않았다. 인증·권한·입력값 공격과 전체 사이트 안전을 평가한 결과는 아니다.

worker와 planner가 결과 저장·완료 도구를 호출하지 않고 문장만 출력해 운영자가 두 차례 메인 에이전트 지시로 fact #8 저장과 hint #9를 보조했다. 그래도 실제 prove_goal 호출은 없었고, 작업은 11:31:34–11:42:48 KST, 674초 후 **timeout·목표 0/1 open**으로 끝났다. 데이터 수집·운영자 검토와 ARTEX 자동 완료 성공을 구분한다. 목표 분해의 잘못된 CIDR 등록 시도·404 헤더에 대한 과도한 일반화도 품질 경고다. 임시 worker 실행 제한은 제거하고 기존 규칙·도구 목록 복원, 실행 중 worker·모델 0을 확인했다. 홈페이지 코드·DB 설정은 변경하지 않았다.

[실측 JSON](results/local-audit-20261029-113134-efada8.json)과 [진단 요약](results/local-audit-20261029-113134-efada8-summary.md)은 Git 제외 로컬 기록이다. 이번 대상 이미지가 앞선 정상 GET 시험 이후 변경됐으므로 동일 환경의 성능·보안 전후 비교로 취급하지 않는다. 실습 VM·pfSense·Snort·Splunk는 미검증이다.

### Qwen 결과 저장·종결 코드 보완 · 2026-10-29

설정 조정만으로는 누락이 재발해, 실제 저장 없이 자연 종료하려는 worker의 제한된 복구와 증명 성공 직후 planner 종료를 코드로 보완했다. 복구 중 새 명령·웹 요청은 차단하며 목표를 자동 승인하지 않는다. 최초 보완 이미지는 `artex-local:completion-20261029-r2`였으며, 실제 홈페이지 재시험 후 현재는 아래 r3 기록을 따른다. 원래 고정 릴리스의 소스·도구·skills를 바탕으로 했으며 로컬 HEAD 전체를 배포한 것은 아니다.

사용자 승인으로 통합검색 `/search.php?q` 한 입력에8GET(정상·따옴표·참/거짓·무해한 XSS표식3종·정상 재확인)을 실행했다. 모든 응답200·Apache8건의 경로/상태/요청ID가 일치했고 DB 전후 데이터 덤프 지문도 동일했다. 정상 검색/재확인179건, SQL참/거짓 각각0건·동일 결과 링크·SQL오류 표식 없음이었다.
