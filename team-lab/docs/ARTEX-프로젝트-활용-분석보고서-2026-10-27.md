# ARTEX 프로젝트 활용 분석 보고서

기준일: 2026년 10월 27일 · Asia/Seoul

대상: 자체 웹사이트와 가상 관제 환경을 준비하는 최종 프로젝트 팀

분석 기준: 공통 기준 v10과 로컬 ARTEX 소스 `fdfb7a17b7da5e2de716c0e98475ec77a41c64c6`

실험 상태: `not_run` · 설치 및 실행 성능 미검증

## 1 활용 방향

**ARTEX는 자체 웹사이트를 대상으로 AI가 시험 방향을 정하고 도구를 실행하며, 발견 내용과 증거를 정리하는 공격 실험 도구로 활용하는 것이 적합하다.** 공격 담당자 1명의 탐색과 기록 업무를 보완하고, 관제 담당자는 그 과정에서 발생한 로그로 탐지정책과 대응 절차를 평가할 수 있다.

팀의 중심 성과는 AI가 공격했다는 사실보다 **어떤 요청이 발생했고, 실제로 무엇이 성공했으며, 관제가 무엇을 탐지·차단했고, 개선 후 무엇이 달라졌는지 설명하는 것**에 둔다. ARTEX의 결과를 웹사이트·네트워크·보안 구성요소·SIEM의 기록과 연결해야 이 성과를 입증할 수 있다.

지속적인 로그 축적에는 다음 역할 분담을 제안한다.

| 실행 구분 | 맡길 일 | 프로젝트에서 얻는 자료 |
| --- | --- | --- |
| 정상 사용자 흐름 | 로그인, 검색, 본인 자료 조회 등 정상 기능을 일정 조건으로 반복 | 정상 기준선, 오탐과 사용자 영향 평가 |
| Kali·Metasploit 및 고정 스크립트 | 선정한 기준 사례를 정해진 조건으로 재현 | 도구별 기준 결과, 정책 변경 전후 비교 |
| ARTEX | 대상 반응에 따라 다음 행동을 선택하는 탐색과 시나리오 수행 | AI의 발견·재현 성과, 실행 과정, 근거와 보고 초안 |
| 관제 및 결과 검토 | 서버·보안 로그 대조, 경보·차단 판정, 정책 개선과 재시험 | 검증된 관제 성과와 최종 보고서 |

Kali·Metasploit과 ARTEX는 독립적인 실행 지점으로 시작한다. ARTEX가 원격 Kali를 자동 조종하는 구성이나 역할별 모델 혼합 운영은 현재 팀의 검증된 구성에 포함되지 않는다. 원안의 AI/ML 학습·평가 요구를 ARTEX 모델 비교만으로 충족할 수 있는지는 멘토에게 별도로 확인해야 한다. [공통 기준][P1]

## 3 ARTEX에서 활용할 수 있는 기능

### 작업 계획과 도구 실행

ARTEX는 Go 서버, Next.js 화면, PostgreSQL 저장소로 구성된다. 계획자인 planner가 다음 시험 방향을 정하고, 실행자인 worker가 도구를 사용해 결과를 기록한다. 발견 자산과 사실을 보관하는 자산 그래프, 작업별 진행과 근거를 보관하는 탐색 그래프를 사용한다. [구조 설명][S1] · [실행 엔진][S2]

우리 팀은 처음부터 이 구조를 다시 개발하기보다 기존 작업 화면, 도구 실행, 발견 기록을 사용하고 프로젝트에 필요한 실행 기록과 관제 결과 연결을 보완하는 편이 효율적이다. 다만 도구는 ARTEX 실행 환경에서 동작하므로, Kali에 설치한 도구가 ARTEX에서도 자동으로 사용되는 것은 아니다. [worker 구현][S3]

### 모델 연결과 비교

소스에는 Anthropic, OpenAI Chat Completions, OpenAI Responses 형식의 연결 경로가 있다. 로컬 모델은 호환 API를 제공하는 Ollama 등을 통해 연결하는 구상이다. API 주소 연결에 성공한 뒤에도 도구 호출, 도구 결과를 읽은 후속 행동, 종료와 보고까지 검증해야 한다. Ollama 역시 OpenAI API의 일부를 지원한다고 명시하므로, 호환 주소만으로 ARTEX 전체 동작을 보장할 수 없다. [모델 구현][S4] · [Ollama 호환 API](https://docs.ollama.com/api/openai-compatibility) · [도구 호출](https://docs.ollama.com/capabilities/tool-calling)

소스의 모델 선택은 역할별 바인딩, 작업 모델 체인, 전역 설정 순으로 이뤄진다. 따라서 같은 ARTEX에서 모델만 바꿔 비교하려면 planner·worker·보고 역할이 실제로 어느 모델을 호출했는지 확인해야 한다. 다른 모델로 자동 전환된 실행은 단일 모델 비교에서 분리한다. [모델 선택 구현][S5]

### 증거와 보고서

ARTEX에는 HTTP 기록 프록시, 취약점과 트래픽 증거 연결, Markdown·CSV·JSON·증거 ZIP 내보내기가 구현돼 있다. 이를 취약점 진단과 모의해킹 결과 보고서의 기초 자료로 사용할 수 있다. [트래픽 증거][S6] · [내보내기 구현][S7]

팀 보고서에는 여기에 **실제 대상 결과, SIEM 경보, 실제 차단, 정상 사용자 영향, 개선 후 재시험 결과**를 추가해야 한다. ARTEX가 생성한 취약점 설명은 검토 대상이며, 보고서 파일 생성 자체가 취약점 입증을 뜻하지 않는다.

### 내장 자동화와 탐지 자료

사용자 정의 에이전트에는 시간 간격, 취약점 발견, 목표 달성, 작업 시간 초과, 도구 호출, 작업 생성에 따른 트리거가 있다. 이 기능을 향후 보조 자동화에 활용할 수 있지만, 대상 초기화·실행 ID 부여·정상/공격 비율 조절·보안 로그 대조·판정을 포함한 팀의 반복 실험 체계는 추가로 설계해야 한다. [스케줄러 구현][S8] · [팀 자동화 준비][P4]

저장소의 Sigma·Suricata 규칙과 지표는 관제 규칙을 검토할 때 참고할 수 있다. 실제 사용할 제품의 로그 필드와 수집 위치에 맞춰 변환·검증해야 하며, 일부 ARTEX 문자열을 잡는 규칙이 모든 웹 공격을 탐지하는 것은 아니다. [탐지 자료][S9]

## 4 우리 프로젝트에서 사용할 흐름

### 배치와 통신 경로 제안

실습 통신의 목표 경로는 **ARTEX 또는 Kali 실행부 → pfSense → 자체 웹사이트**다. 공격측·피해측 가상망을 나누고, 실제 출발지와 경유 여부를 확인해야 한다. 개인 노트북의 관리 접속과 이 실습 경로는 별도로 설계한다. 같은 Wi-Fi에 연결됐다는 이유로 VMware Host-only VM 접근이나 pfSense 경유가 성립하지는 않는다.

| 배치 후보 | 활용 방법 | 선택 전에 확인할 조건 |
| --- | --- | --- |
| Mac에 ARTEX·PostgreSQL, Mac 네이티브 Ollama | 기존 준비 예시를 이용해 로컬 추론과 실행을 분담 | ARTEX 컨테이너의 Ollama 접근, VMware 실습망 도달, pfSense 경유, 동시 자원 사용 |
| 공용 서버의 별도 VM에 ARTEX 실행부, Mac에 Ollama | 공격 실행부를 실습망에 배치하고 추론을 분리 | 공용 서버 자원, 실행 VM에서 Mac 모델 API 접근, 모델 통신과 공격 통신의 경로 구분 |

두 안 모두 배치 후보이며, 현재 최종 배치는 미정이다. 프론티어 API나 로컬 모델로 보내는 추론 요청과 웹사이트에 보내는 시험 요청을 구분해 경로·통신량·비용을 기록한다. [공통 환경 구상][P1] · [초기 구성 예시][P2]

### 한 번의 실험 절차

1. **대상 준비:** 기능과 정상 권한 규칙, 더미 자료, 취약 또는 수정 상태, 초기 상태 ID를 정한다.
2. **실행 조건 기록:** 시나리오, 도구·모델 버전, 시간·요청·동시성 한도, 관제정책 버전을 실행 ID에 연결한다.
3. **정상 대조 확인:** 정상 요청이 예상대로 동작하고 필요한 로그가 수집되는지 확인한다.
4. **ARTEX 수행:** 범위를 정한 단일 작업을 실행하고 실제 도구 결과와 요청을 보관한다.
5. **대상 결과 판정:** 공격 담당자와 대상 담당자가 실제 자료 반환·권한 경계·상태 변화를 확인한다.
6. **관제 결과 판정:** 관제 담당자가 예상 관측 위치의 로그와 경보·차단을 확인한다.
7. **보고 및 재시험:** 근거를 검토하고, 사이트 수정 또는 관제정책 변경 후 동일 조건으로 재시험한다.

지속 로그 축적은 이 절차를 통과한 사례부터 확대한다. 정상·기준 공격은 일정한 반복을 맡고, ARTEX는 시간과 요청 예산을 정한 개별 탐색을 맡게 한다. AI가 선택하는 요청 수와 경로는 실행마다 달라질 수 있으므로, ARTEX만으로 일정한 요청률과 정상/공격 비율을 맞추는 운영은 우선순위에서 낮춘다.

## 5 필요한 준비물과 추가 작업

### 역할별 준비

아래 담당 구분은 관제 인프라 3명, 대상 구축 1명, 공격 실행 승현 1명이라는 현재 역할 구상을 따른 제안이다. 개인별 공식 업무 배정과 일정은 팀에서 정한다.

| 준비 주체 | 우선 필요한 것 | 준비 완료를 확인할 자료 |
| --- | --- | --- |
| 대상 구축 | 실제 기능·스택·DB·인증 구조, 계정별 권한표, 더미 계정과 자료, 취약/수정 상태, 로그, 초기화 방법 | 정상 기능 확인표, 기준 상태 ID와 복구 확인 |
| 관제 인프라 | VM 배치와 가상망, pfSense 경유, 실제 출발지, 수집할 로그, IDS/IPS 필요 여부와 위치, SIEM 제품·파서·규칙 | 정상 요청의 경로 근거, 수집 로그와 필드 매핑 |
| 공격 담당 | 배포 버전, 모델과 도구 호출, 실행 한도·중단, 시나리오 지시, 정상 대조, 증거와 보고 검토 | 단일 작업의 실행 기록과 검토된 결과 |
| 공동 결정 | 첫 시나리오, 반복 속도·비율·시간·보존량, 보고 주기와 검토자, AI/ML 요구 충족 방법 | 합의한 실험 조건과 평가표 |

pfSense의 방화벽 통과·차단과 애플리케이션 취약점 탐지는 구분한다. 객체 권한 문제는 서버의 계정·객체 소유권 기록이 필요하고, HTTPS 내용 기반 탐지는 센서가 실제로 볼 수 있는 범위를 따져야 한다. 방화벽 로그만으로 모든 웹 취약점을 판정하도록 설계하지 않는다.

### 소프트웨어와 장비

| 구성 요소 | 필요 이유 | 현재 결정 또는 검증할 내용 |
| --- | --- | --- |
| ARTEX 실행 환경 | 서버와 실제 도구 실행 | Docker 배포 또는 실행 VM, CPU 아키텍처, 도구 포함 여부 |
| PostgreSQL과 보존 공간 | 작업·자산·발견 저장 | DB 볼륨과 ARTEX `data/`의 백업·복구, 저장 한도 |
| Ollama와 로컬 모델 | 로컬 추론 비교 | 버전·모델 digest·실제 문맥·메모리·도구 호출 |
| 프론티어 API | 프론티어 모델 비교 | 공급자·모델·키 보관 위치·사용 예산·지원 형식 |
| 웹사이트와 로그 | 시험 대상과 결과 정답 제공 | 정상 기능, 더미 자료, 로그 필드와 시각, 초기화 |
| pfSense와 선택 센서·SIEM | 경로 통제와 관제 | 실제 경유, 관측 위치, 제품 선정, 파싱과 경보 |

Mac은 공통 기록상 M4 Pro·통합 메모리 24GB다. 모델 가중치 외에도 문맥, Docker, PostgreSQL, 브라우저와 운영체제가 메모리를 사용하므로 모델 단독 동작과 전체 조합을 단계적으로 측정한다. 공용 서버의 사양은 다시 확인해야 하며, 과거의 i5·16GB 장비 정보만으로 이번 본체의 수용량을 확정할 수 없다. [장비 기록][P1]

현재 로컬 후보는 `qwen3:8b`, 실제 문맥 32768, 작업 1개·worker 1개·동시 추론 1개다. 이는 최초 검증안이다. Ollama 공식 문서는 에이전트 등 큰 문맥이 필요한 작업에 64,000토큰 이상을 권고하므로, 32K를 장시간 ARTEX 작업에 충분한 값으로 확정하지 않는다. 자원이 허용하는 범위에서 문맥 압축·누락·오류와 작업 품질을 확인한 후 조정한다. [후보 설정][P5] · [Ollama 문맥 안내](https://docs.ollama.com/context-length)

프론티어 비용은 실제 입력·출력 토큰과 선택 시점의 공급자 단가로 계산한다. 로컬 실행은 API 사용료와 별개로 메모리·실행 시간·장비 점유를 기록한다. 현재 자료로 모델별 비용이나 처리량을 수치로 제시할 수는 없다.

### 기존 기능을 사용하고 보완할 부분

| 구분 | 사용할 것 또는 추가할 것 | 우선순위 |

기존의 `run-record.json`, `run-summary.csv`, `report.md`를 공통 기록의 출발점으로 사용할 수 있다. 자동화 개발은 이 양식과 판정 흐름을 실제 단일 실행에서 확인한 뒤 진행하는 순서가 적절하다. [기록 양식][P6] · [결과 보고 양식][P7]

## 6 먼저 선정할 시나리오

전체 조사 목록을 한꺼번에 구현하기보다 대상 기능과 정답이 명확한 소수 사례부터 시작한다. 기존 19개 분류·51개 하위 시험은 조사 범위이며 필수 구현 수량이 아니다.

| 후보 | 대상 측 준비물 | 정상 대조 | 핵심 판정과 근거 |
| --- | --- | --- | --- |
| W01 서비스·웹 경로 정찰 | 서비스와 공개 경로의 정답 목록 | 공개 기능에 대한 정상 접근 | 실제 존재하는 항목 발견 여부, 잘못 보고한 항목, 요청과 서버 로그 |
| W04 객체 접근 권한 | A·B 계정, 각자의 비공개 더미 자료, 권한표 | 본인 소유 자료 조회 | 다른 계정 자료의 실제 반환 여부, 계정·객체·서버 기록 |
| W05 SQL 주입 | SQL DB를 쓰는 분리된 실습 검색 기능과 더미 자료 | 정상 검색 결과 | 허용 조회 범위를 벗어난 결과와 앱·DB 측 근거 |

W05는 실제 스택이 SQL DB를 사용할 때 채택한다. 조건이 맞지 않으면 로그인 제한, 기능 권한, XSS, 파일 경로 등 기존 후보에서 대상 기능에 맞는 사례를 선정한다. W01의 발견 성과와 W04·W05의 취약점 재현 결과는 분리해 평가한다. [시나리오 초안][P3]

첫 사례로 W04를 택한다면 대상 담당자는 A·B와 비공개 더미 자료, 관제 담당자는 인증 주체·객체 ID가 남는 로그, 공격 담당자는 두 계정의 정상 대조와 시험 조건을 준비한다. 단순히 경로가 열렸거나 HTTP 200이 반환됐다는 사실보다 **누구에게 어떤 자료가 반환됐는지**를 판정 기준으로 삼는다.

## 7 소스에서 확인된 주요 제약

### 대상 범위와 요청 한도

소스의 작업 제약은 에이전트에 전달하는 지시 맥락이고, guard에는 이전 RoE 범위 강제 기능이 제거됐다는 설명이 있다. 규칙이나 판정기가 적용되지 않는 경로에서는 호출이 허용될 수 있다. 따라서 지시문과 작업 범위 입력에 더해, 실행부의 네트워크 접근 범위와 실제 요청 한도를 통제·검증하는 장치가 필요하다. [제약 구현][S10] · [guard 구현][S11]

`rate_per_second`와 `rate_per_minute`는 LLM API 호출률이다. 대상 웹사이트의 HTTP 요청률과 개수 제한으로 사용할 수 없다. worker 수·작업 시간 제한도 대상 요청 개수의 엄격한 상한과는 다르므로, 선정한 요청 경로에서 계수·제한이 실제 적용되는지 확인한다. [모델 설정 구현][S4]

### 증거 기록과 차단 판정

HTTP 캡처와 LLM 원문 기록은 기본적으로 꺼져 있다. 기록 프록시를 사용해도 HTTPS 처리 오류 뒤 투명 전달로 전환되면 해당 호스트의 통신은 계속되면서 내용 기록이 빠질 수 있다. 비HTTP 도구 실행은 별도 네트워크·서버 근거가 필요하다. [기본 기록 설정][S12] · [프록시 구현][S13]

그러므로 요청 성공을 기록 성공으로, 응답 실패를 방화벽 차단으로 간주하지 않는다. ARTEX 내부 도구 통제가 실행을 막은 사례도 대상 방어 장비의 차단과 구분한다. 특정 지점에서 차단됐다면 그 뒤 서버에 로그가 없는 것은 정상일 수 있으므로, 실행별 예상 관측 위치를 먼저 정한다.

### 버전과 실험 상태

현재 Compose는 `ghcr.io/jiwoochris/artex-global` 이미지를 기본 `latest`로 참조한다. 팀 조직의 포크 소스가 자동으로 이미지에 반영되는 구조가 아니며, 호스트의 `skills/`가 이미지 내부 경로를 덮어쓴다. 기존 배포 후보와 로컬 소스도 일치하지 않는 것으로 기록돼 있어, 실제 사용할 이미지 digest·소스·skills 기준을 맞춰야 한다. [Compose][S14] · [버전 기록][P5]

새 작업 생성만으로 이전 발견과 공유 지식이 모두 초기화되지는 않는다. 모델 비교 전 웹사이트의 데이터·세션과 ARTEX의 작업·공유 자산·발견·메모리·파일에서 복구할 범위를 정한다. 기본 작업 보고서의 자산 수는 전역 자산을 집계하므로, 이를 각 실행의 신규 발견량으로 그대로 사용하지 않는다. [작업 보고서 구현][S15]

HTTP 원문에는 계정·세션·더미 자료가 포함될 수 있다. 실험 원본은 Git 제외 경로인 `team-lab/results/`, `team-lab/evidence/` 등에 보관하고 공유 보고서에는 검토한 근거를 연결한다. 실제 비밀값·운영 데이터는 예시 파일에 넣지 않는다.

## 8 평가 기준과 산출물

### 분리해서 기록할 결과

| 평가 항목 | 판정할 내용 |
| --- | --- |
| 실행 완료 | 모델 연결·도구 호출·종료·저장까지 정상 수행됐는가 |
| 정찰 발견 | 정답 목록의 무엇을 찾았고, 무엇을 잘못 보고했는가 |
| 취약점 재현 | 대상 측 근거로 선정한 성공 조건이 확인됐는가 |
| 탐지 경보 | 실제 발생한 시험에 대응하는 경보가 생성됐는가 |
| 실제 차단 | 지정한 방어 구성요소가 요청 또는 공격 효과를 막았는가 |
| 정상 사용자 영향 | 정상 기능에서 경보·차단·오류·지연이 발생했는가 |
| 자원과 비용 | 시간, 요청 수, 모델 호출·토큰, 메모리·스왑, 오류와 사용료는 얼마인가 |
| 증거 완전성 | 실행과 대상 결과·관제 판정을 설명하는 근거가 연결됐는가 |

로그가 수집되지 않은 상태, 파싱에 실패한 상태, 로그는 있으나 경보가 없는 미탐 상태를 나눈다. 결과가 판정 불가인 실행도 전체 실행 기록에 남겨, 분석 가능한 사례만 골라 성공률을 높여 보이지 않도록 한다. 현재 위 항목의 실측값은 모두 미평가다.

### 모델 비교와 정책 개선

모델 비교에는 같은 ARTEX·도구·지시문·권한·대상 초기 상태·관제정책·시간 및 요청 예산을 사용한다. 알려진 시나리오를 수행하는 시험과 취약점 정보를 제공하지 않는 자율 탐색 시험은 분리한다. 조건이 다른 두 결과를 하나의 모델 순위로 합치지 않는다.

여건이 되면 모델·시나리오별 여러 회를 반복하고 실행 순서를 번갈아 배치한다. 예비 비교는 조건별 3회 정도를 시작안으로 삼을 수 있으나, 이 횟수로 일반적인 성능 우위를 확정하지는 않는다. 실제 호출 모델, 자동 전환, 초기화 실패도 함께 남긴다.

지표는 사전에 단위를 정한다. 유효 공격 실행은 실제 시험 시도가 확인된 실행이며, 침해 성공을 요건으로 삼지 않는다. 예를 들어 시나리오 실행 단위의 탐지율은 **경보가 확인된 유효 공격 실행 수 ÷ 탐지 평가가 가능한 유효 공격 실행 수**, 정상 경보율은 **경보가 발생한 정상 실행 수 ÷ 평가 가능한 정상 실행 수**로 계산할 수 있다. 제외·판정 불가 건수와 이유를 같이 제시하고, 요청 단위 집계와 혼합하지 않는다. 정상 차단율은 경보율과 따로 계산한다.

관제정책 개선 효과는 대상 취약 상태를 유지하고 기록한 동일 요청·사용자 흐름을 재현해 정책 전후를 비교한다. ARTEX를 새로 자율 실행해 변경된 정책에 적응하는지 보는 평가는 별도 시험으로 관리한다. 사이트 수정 효과는 관제정책을 유지한 채 취약/수정 상태를 비교한다. 두 요소를 동시에 바꾼 경우에는 어느 변경의 효과인지 단독으로 해석하지 않는다.

### 연결할 최종 산출물

1. 환경과 버전 명세: 실제 배치, 통신 경로, 이미지·skills·모델 버전, 보존 위치.
2. 시나리오 카드: 기능, 정상 규칙, 성공 조건, 정상 대조, 한도, 초기화 방법.
3. 실행별 기록과 증거 목록: 실행 ID, 대상·유형·일자·실제 결과, 관련 로그와 ARTEX 작업 ID.
4. 취약점 진단 및 모의해킹 결과: 재현 근거, 영향, 수정 권고와 검토자.
5. 관제 개선 보고: 탐지·차단·정상 영향, 정책 변경 근거와 재시험.
6. 모델 비교 보고: 실제 사용 모델별 성과·오류·자원·비용과 비교 조건.

## 9 단계별 추진 제안

실제 프로젝트 시작·종료일은 미정이므로 아래는 날짜를 확정하지 않은 진행 순서다. 멘토링의 3주차 목표인 환경과 실제 로그 기반 차단·통과 확인을 우선하고, 추가 모델 비교와 자동화는 준비 정도에 맞춰 확장한다.

| 단계 | 진행할 일 | 다음 단계로 넘어갈 근거 |
| --- | --- | --- |
| 1 대상과 범위 결정 | 첫 기능·시나리오, 정상 규칙, 배치·버전·자원·예산 결정 | 실험 카드와 환경 결정표 |
| 2 기본 동작 확인 | 구축 요청 이후 모델 응답·도구 호출·무해한 작업·보고서 저장 검증 | 실제 호출과 저장 결과 |
| 3 경로와 수집 확인 | 정상 요청으로 출발지·pfSense 경유·대상 도달·로그 확인 | 경로 자료와 수집 로그 대조 |
| 4 단일 사례 완성 | 정상 대조·고정 기준 실행·ARTEX 단일 실행·결과 검토 | 대상 결과와 관제 판정이 연결된 보고서 1건 |
| 5 개선과 모델 비교 | 초기화, 정책 개선 전후 재시험, 로컬·프론티어 비교 | 조건을 통제한 반복 결과 |
| 6 지속 운영 확대 | 반복 관리, 비율·속도·보존량·중단 기준, 집계 자동화 | 누적 실행 기록과 품질 점검 |

**가장 먼저 필요한 것은 첫 대상 기능과 정상 규칙, 실제 실행 경로, 사용할 버전·모델, 결과를 입증할 로그다.** 이 네 가지를 정하고 근거가 연결된 단일 사례를 완성하면, 그 구조를 다른 시나리오와 반복 자동화로 확장할 수 있다.

## 근거 자료

- 프로젝트 판단과 준비 상태: [공통 기준][P1], [팀 준비 안내][P2], [설치 전 점검표][P8].
- 팀 실험 설계와 양식: [시나리오][P3], [자동화 준비][P4], [버전 기록][P5], [실행 기록][P6], [결과 보고 양식][P7].
- 기능 근거: 아래 소스 링크는 분석 기준 커밋에 고정했다. 공개 저장소의 소개나 예시 성능을 팀의 실측 결과로 사용하지 않았다.
- 외부 호환성 참고: [Ollama OpenAI 호환 API](https://docs.ollama.com/api/openai-compatibility), [도구 호출](https://docs.ollama.com/capabilities/tool-calling), [문맥 길이](https://docs.ollama.com/context-length). 확인일 2026년 10월 27일.
