# ARTEX 공격자 운영 설계

2026-10-31 멘토 시나리오 후속 · 2026-11-03 소스 대조 갱신 · 실제 등록·대상 실행: `not_run`

## 시연에서 보여줄 ARTEX의 역할

사용자가 목표와 허용 범위를 주면 planner가 조사 방향을 정하고, worker가 해당 방향에 맞는 도구를 선택해 실행한다. worker는 관측 결과를 기록하고 planner는 그 근거로 다음 방향 또는 완료 여부를 판단한다. 고정 명령을 대신 실행한 경우와 관측을 보고 다음 행동을 선택한 경우를 구분해 보여준다.

현재 소스에서 확인한 기본 경로는 다음과 같다. 실제 모델이 매번 이 경로를 정확히 수행한다는 보장은 아니며 호출 이력으로 검증한다.

`목표·범위 → planner add_intent → worker 도구 선택 → 실제 실행·결과 → insert_assets / record_fact → planner 검토·후속 의도 또는 prove_goal → 실제 보고서 저장`

- 새 서비스·경로 자체는 `insert_assets`, 관측·판단은 `record_fact`, 실제 재현 근거가 있는 취약점은 `report_finding`으로 구분한다. 패치된 PHP에 보낸 공격 시도와 거부 응답은 사실로 남길 수 있지만 취약점 발견으로 등록하지 않는다.
- planner는 실행 방향과 근거를 관리하고 최초 제안에서는 worker 하나로 순차 진행한다. Mac에서 과거 1작업·1worker 구성이 확인됐지만 현재 Mac/VM의 실제 설정과 활성 모델은 실행 전에 다시 확인한다. Windows GPT-OSS 32K 로드 보고를 실제 worker 진단 성과로 이월하지 않는다.
- 자산 그래프는 여러 작업이 공유할 수 있으므로 이전 작업의 자산과 현재 실행의 새 발견을 구분한다. 과거에 찾은 주소를 현재 요청한 증거로 쓰지 않는다.

## 기존 도구를 먼저 사용한다

ARTEX에 독립적인 네트워크 스캐너가 기본으로 존재한다고 가정하지 않는다. 현재 worker는 Bash 및 WebFetch 등의 실행 기능과 자산·사실 기록 도구를 조합한다. 설치된 도구나 skills/MCP가 제공하는 추가 기능은 실제 목록을 확인한다.

첫 확인은 기존 기능으로 제한된 정상 응답과 공개 경로를 확인하는 방식이다. nmap은 지정 서비스 확인이 필요할 때, sqlmap은 승인된 입력의 SQLi 비교가 필요할 때만 추가한다. sqlmap은 포트 스캐너가 아니라 실제 입력 공격 요청을 보내는 도구다. Kali의 도구는 ARTEX 실행 환경의 도구가 아니며, 원격 자동 조종을 구현된 것으로 취급하지 않는다.

## 사용자 정의 도구 화면에서 준비하는 방법

현재 웹 소스의 경로는 `/system/tools`이며 한국어 화면은 **도구 → 사용자 정의 도구 → 사용자 정의 도구 만들기**다. 화면 라벨은 `web/messages/ko.json`, 편집·저장 동작은 도구 페이지 소스와 대조했다. 실제 Mac 화면 확인이나 등록을 수행한 기록은 아니다.

| 화면 항목 | nmap 예시 | sqlmap 예시 |
| --- | --- | --- |
| key | `fiveeyes_nmap_scan` | `fiveeyes_sqlmap_check` |
| 유형 | `script(Python 스크립트)` | 동일 |
| 설명(모델에 전달) | 예시 JSON `description` | 예시 JSON `description` |
| Python 본문 | 예시 JSON `exec.code` | 예시 JSON `exec.code` |
| 타임아웃(ms) | 예시 JSON `exec.timeout_ms` | 예시 JSON `exec.timeout_ms` |
| 파라미터 JSON Schema | 예시 JSON `schema` | 예시 JSON `schema` |
| 에이전트 연결 | 최초 준비는 미연결, 실행 시 worker만 검토 | 동일 |
| 활성화 | 준비 단계는 끔 | 동일 |
| deferred | 최초 소규모 시연은 끔 | 동일 |

전체 JSON을 Python 본문 칸에 붙이지 않는다. 각 JSON 필드를 해당 화면 항목으로 옮긴다. 신규 편집창은 활성화가 기본 켜짐이므로 비활성 예시를 준비할 때는 직접 끈다. `테스트 실행`은 저장 없이 실제 코드를 실행하는 기능이며 네트워크 dry-run이 아니다.

두 예시 파일은 [스캔 예시 폴더](../config/scan-tools/README.md)에 있다. API는 `POST /api/tools/custom`, 수정은 `PUT /api/tools/custom/{key}`이고 요청 필드는 `key`, `description`, `schema`, `agents`, `enabled`, `kind`, `exec`, `deferred`다. 등록 자체는 설치를 수행하지 않는다. 등록 API나 화면을 이번 작성에서 사용하지 않았다.

모델은 도구의 이름·설명·파라미터 schema를 읽고 인수를 생성한다. `target` 또는 `url`, `run_id`만 받도록 예시를 좁혔고 실제 실행 코드 내부의 대상 목록은 비어 있다. 범위가 정해진 후 운영자가 검토된 비공개 복사본의 승인 대상과 포트·변수를 고정해야 하며, 모델이 자유 명령·임의 옵션을 입력하는 방식이 아니다.

`shell` 유형은 설치된 CLI를 Bash에서 호출할 수 있다고 모델에 알리는 선언이다. 별도 호출 가능한 도구나 설치를 만들지 않는다. `script` 유형은 자체 이름으로 실제 호출·인수·결과가 남아 발표와 검증에 쓰기 쉽다. 실행 시 서버가 Python을 선택하고 파라미터를 stdin JSON으로 전달한다. 예시 코드는 shell 문자열 대신 argv 배열로 nmap/sqlmap을 실행한다.

## 실제 실행과 완료 근거의 연결

서버의 도구 조립은 활성화와 agent 연결을 확인한 뒤 worker에게 도구를 제공한다. `deferred=true`이면 schema를 처음부터 모두 보여주는 대신 추가 도구 검색·실행 경로를 사용한다. 첫 시연에서는 동작을 단순하게 확인하기 위해 deferred를 끄는 것을 기본안으로 둔다.

현재 목표 근거 판정은 사용자 정의 도구 이름을 제외한다. 도구 호출 trace와 fact는 검토할 수 있으나 사용자 도구 결과만으로 자동 `prove_goal` 완료를 지원한다고 주장하지 않는다. 현재 카탈로그를 전역 hook에서 조회해 허용하는 방식은 서버 간 DB 혼선과 실행 후 도구 변경·재생성 문제가 있어 채택하지 않았다. 향후 서버·작업별로 실행 당시 도구 정의와 종류를 보존하고 엄격한 실행 결과를 검증하는 연결이 필요하다.

2026-11-03 작업 소스에서는 Python 프로세스 오류·timeout이 오류로 전달되게 보완하고 Unix 취소 시 Python 및 일반 자식 프로세스를 같은 그룹에서 정리한다. Windows는 taskkill의 트리 종료를 사용하되 native 검증은 후속 항목이다. 이 소스가 Mac 실행 이미지에 적용됐는지는 별도 배포·검증 항목이다.

`record_fact` 저장 성공은 도구 실행이나 취약점 성공을 증명하지 않는다. `prove_goal`은 실제 근거가 목표 범위를 충족할 때만 사용한다. 보고서 목표는 성공한 `Write`와 현재 Markdown 파일 내용 일치를 확인하는 기존 경계를 유지한다. 사용자 도구는 `Write` 대신 보고서 저장을 증명할 수 없다. 실행 근거 검사는 관측 내용의 의미적 정확성까지 보장하지 않으므로 원본 결과를 검토한다.

## 고정 기준 실험과 ARTEX 판단 실험의 비교

| 항목 | 고정 기준 실험 | ARTEX 판단 실험 |
| --- | --- | --- |
| 사람이 제공 | 승인 대상·도구·입력·순서와 대조 사례 | 같은 승인 대상·도구·허용 범위·한도·목표 |
| ARTEX 선택 | 정해진 실행·결과 기록 | 허용된 후보 중 다음 조사 방향·도구·순서를 선택 |
| 확인할 것 | 실제 실행, 서버 기록과 결과 기록 일치 | 선택 이유, 관측에 따른 다음 행동, 중복·오판·범위 준수 |
| 성과 | 도구 연결 및 재현 가능한 기준선 | 근거가 있는 후속 판단과 과업 완주 |

동일 초기 상태·모델·도구 버전과 정상 대조를 사용하고 운영자의 추가 힌트·대신 저장·종료 보조를 기록한다. 입력이나 수집기를 운영자가 설계했다면 소스 참고/운영자 설계 실험으로 표시한다. 단순 도구 호출만으로 자율 탐색 성과를 주장하지 않는다.

## 시연 장면과 완료 조건

1. **목표 입력:** 허용 대상과 범위, 발견·기록할 내용을 보여준다. 목표와 한도가 실제 실행 도구에 적용 가능한지 확인한다.
2. **계획 분해:** planner가 만든 intent를 보여준다. 실행하지 않은 설명과 실행할 의도를 구분한다.
3. **도구 선택:** worker 호출 이력에서 실제 도구 이름·인수를 보여준다. 화면의 도구 등록 카드나 모델의 예고 문장은 실행 증거가 아니다.
4. **결과 확인:** 동일 호출 ID의 결과, 도구 exit_code·상태와 서버 측 기록을 대조한다. nmap의 run_id는 패킷에 자동 포함되지 않으므로 출발지·대상·포트·시각을 사용한다.
5. **후속 판단:** 관측에서 새 사실을 저장하고 planner가 이를 바탕으로 다음 의도 또는 중단을 선택했는지 보여준다. 공격이 거부됐다면 거부 근거를 기록한다.
6. **보고·종결:** 실제 보고서 파일과 사실·목표 상태를 확인한다. 도구 성공, 취약점 성공, 관제 탐지는 별도 판정으로 남긴다.

완료 증거는 `task_id / intent_id / worker / tool / tool_use_id / 인수 / 원본 결과 / 독립 서버 기록 / fact_id / 목표 상태 / 실제 보고서 경로 / 운영자 보조`다. 누락·미설치·timeout·보고서 저장 실패는 그대로 기록한다. 현재 모든 실제 등록·대상 실행 결과는 `not_run`이다.

한 작업의 정상 완료가 ARTEX 전체 진단 정확성을 입증하지 않는다. 현재 일반 작업 프롬프트는 대상 요청 횟수를 강제하는 장치가 아니며, nmap rate와 sqlmap delay·timeout도 엄격한 전체 요청 수 상한이 아니다. 제한된 도구 외의 Bash 등 다른 실행 경로를 포함해 실제 범위와 계수 수단을 실행 전 확인한다.
