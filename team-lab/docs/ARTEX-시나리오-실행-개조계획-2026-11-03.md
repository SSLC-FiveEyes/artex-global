# ARTEX 시나리오 실행 개조 계획

> 2026-11-03 사용자 방향 변경: ARTEX 자율성을 위해 `armed`에서는 Bash·WebFetch를 제공하고 `draft`에서는 실행을 막는다. 아래 기존 전용 어댑터 중심 제한 설명은 이전 설계다. 이 변경만으로 대상이나 인터넷 접근은 제한되지 않으며, 독립된 실습망의 송신 제한과 실제 경로 검증은 별도 미완료다. 배포·대상 실행은 not_run이다.

- 작성일: 2026-11-03 · Asia/Seoul
- 상태: **1차 소스 구현·선택 단위 검증 완료 · 배포와 대상 실행은 `not_run`**
- 담당 경계: 이 문서는 ARTEX의 도구·실행통제·증거화만 다룬다. 피해 웹사이트의 기능·취약 환경·관제 룰·EDR 제품은 다른 담당 범위다.

## 1. 왜 ARTEX를 고치는가

프로젝트의 차별점은 AI가 임의 명령을 많이 실행하는 것이 아니라, 승인된 공격 시나리오 안에서 관측을 바탕으로 다음 행동을 선택하고 그 흔적을 관제팀이 재검증할 수 있게 남기는 데 있다.

현재 ARTEX에는 planner/worker, HTTP·Bash, 사용자 정의 도구, 사실·자산·발견 기록, 작업 활동 이력이 있다. 반면 다음 두 경계는 아직 부족하다.

1. 사용자 정의 도구의 승인 대상 제한만으로는 일반 `Bash`·`WebFetch` 경로를 막을 수 없다.
2. 실행 시점의 도구 정의·입력 지문·서버가 확인한 종료 상태가 한 묶음으로 고정되지 않는다.

따라서 사용자 정의 도구의 출력 문구를 곧바로 신뢰하거나 `prove_goal`의 근거로 열어 두지 않는다.

## 2. 목표 구조

```text
시나리오 실행 프로필
  └─ 허용 도구 / 대상·메서드·포트 / 요청·시간 한도 / 중지 조건 / 필요 증거
       └─ ARTEX worker의 도구 노출·실행 게이트
            └─ 서버 생성 실행 영수증
                 └─ ARTEX 활동 이력 + 원본 결과 + 독립 서버/네트워크 기록
```

실행 영수증은 다음을 뜻한다.

- **도구 실행됨**: ARTEX 서버가 특정 도구를 특정 입력 지문으로 실행했고, 종료·시간초과·오류 상태를 기록했다.
- **취약점 확인됨**: 위 기록만으로는 성립하지 않는다. 대상 서버 또는 격리 수집기의 별도 근거가 필요하다.
- **관제 탐지됨**: 공격자 측 기록과 별개의 판정이다. Snort·웹 로그·EDR·SIEM 측 근거가 필요하다.

## 3. 시나리오별 ARTEX 역할

| 시나리오 | ARTEX가 할 일 | 초기에 허용할 방식 | 실행 전 선행 조건 |
| --- | --- | --- | --- |
| 서비스·웹 경로 탐색 | 응답을 비교해 다음 조사 대상을 판단하고 발견 자산을 기록 | 고정된 단일 대상·포트·경로의 읽기 전용 확인, 필요 시 제한된 nmap 어댑터 | 실제 대상·포트·요청 수·속도·중지 기준·경유 로그 |
| MFA 우회 시도 | 정상/누락/변조/다른 세션/재사용의 결과를 분리해 기록 | 정해진 테스트 케이스만 받는 HTTP 어댑터 | 합성 계정, 모의 인증 방식, 세션 초기화·로그 보관 규칙 |
| 사진 첨부·웹셸 모의 | 격리 복제본에서 업로드·접근·후속 모의 행위의 증거를 연결 | 무해 표식 파일과 고정된 모의 수신지로 제한한 단계형 어댑터 | 격리 복제본, 시험용 파일·프로세스·수신지, 복구 절차 |
| 최근 PHP CVE | PHP 버전·SAPI·패치 상태를 CVE 영향 조건과 대조 | 읽기 전용 평가 카드와 승인된 재현 템플릿 | 별도 격리 시험 환경, 공식/검증된 재현 조건, 서비스 중지 기준 |

웹셸과 PHP CVE의 실제 실행 도구는 지금 만들지 않는다. 격리 대상과 안전 한도 없이는 HTTP 요청 하나를 실제 웹셸·CVE 성공으로 표현할 수 없기 때문이다.

## 4. 구현 단계

### 단계 A — 실행 결과의 신뢰성 기반 (현재 착수)

1. Python 사용자 도구의 exit failure·timeout을 `is_error`로 전달하고, Unix 자식 프로세스를 함께 종료한다. Windows 구현은 교차 컴파일까지만 되어 있으며 Windows 네이티브 검증은 후속이다.
2. 서버가 사용자 정의 도구마다 실행 영수증을 만든다. 영수증에는 도구 키·종류·정의 지문·입력 지문·시작/종료 시각·러너 종료 상태·원본 출력 지문을 담는다.
3. `not_run`, timeout, 오류, 스크립트가 스스로 출력한 성공 문구를 목표 완료 근거로 인정하지 않는 현재 정책을 유지한다.

2026-11-03 소스 반영:

- 사용자 정의 `command`·`script`·`http` 호출은 서버가 만든 `artex_execution_receipt`로 감싼다. 영수증에는 도구 정의 SHA-256, 입력·출력 SHA-256, 시작/종료 시각, runner outcome, `run_id`와 연결된 시나리오 프로필 지문(있을 때)을 기록한다.
- 프로필이 적용된 task의 활동 이력에는 tool-use/result를 포함한 실행 단계마다 시나리오 ID·프로필 상태·프로필 SHA-256 메타데이터를 붙인다.
- 기존 Python 도구의 exit failure·timeout은 `is_error=true`로 전달되며, Unix는 자식 프로세스 트리를 정리한다. Windows `taskkill` 경로는 소스에만 있고 Windows 네이티브 검증은 아직 하지 않았다.
- 이 영수증은 실행 상태를 뜻할 뿐, 웹 취약점·웹셸·PHP CVE 성공이나 관제 탐지를 증명하지 않는다.

### 단계 B — 시나리오 실행 프로필과 도구 게이트

1. 작업마다 프로필을 연결한다. 프로필은 `draft`와 명시적 승인 후의 `armed` 상태를 구분한다.
2. `armed` 프로필에서는 worker에게 프로필의 허용 도구만 노출한다. 자유 `Bash`·`WebFetch`는 기본적으로 제외하며, 보고서 저장에 필요한 비네트워크 도구만 별도로 허용한다.
3. 알려진 도구는 실행 시에도 프로필·입력·한도를 재검사한다. 화면의 도구 카드, 모델의 계획 문장, 등록된 사용자 도구는 실행 승인 자체가 아니다.
4. 각 실행 시 도구 정의와 프로필의 해시·버전을 활동 이력에 남긴다.

2026-11-03 소스 반영:

- 작업별 `task_scenario_profiles` 저장 모델과 `GET/PUT/DELETE /api/tasks/{id}/scenario-profile` 백엔드 API를 추가했다. 아직 실행 중인 Mac DB·UI에는 적용하지 않았다.
- 프로필이 없는 기존 작업은 기존 동작을 유지한다. 프로필이 `draft`이면 task agent의 도구 목록은 비어 있어 실행을 멈춘다. `armed`일 때만 프로필의 정확한 allowlist가 worker·planner·main agent 모두에 적용된다.
- `Bash`, `WebFetch`, 웹 검색, 대화형 shell, MCP 및 임의 이름의 사용자 도구는 프로필에서 허용할 수 없다. 안전한 기록 도구와 `fiveeyes_`로 시작하는 제한형 어댑터만 후보로 둔다.
- 이 단계는 아직 중앙 IP/경로/요청 수 검증을 구현하지 않는다. 그러므로 프로필을 실제로 `armed`로 바꾸기 전에는 각 `fiveeyes_` 어댑터가 서버 측 범위 검사를 갖추는 단계 C가 필요하다.

### 단계 C — 제한형 시나리오 어댑터

- 정찰: 고정 IP/포트/경로와 최대 요청 수를 받는 어댑터부터 만든다.
- MFA: `normal`, `missing`, `tampered`, `cross_session`, `replay`처럼 고정 케이스만 수행한다. 인증 비밀값은 ARTEX 입력·캡처·출력에 넣지 않는다.
- 웹셸 모의: 일반 명령 실행기가 아닌, 격리 대상의 표식 파일·접근·모의 연결을 각각 확인하는 단계형 어댑터로 만든다.
- PHP CVE: 우선 환경 비교 카드만 만들고, 재현 도구는 별도 승인된 검증 조건이 생긴 뒤 추가한다.

### 단계 D — 검증·이관

1. 네트워크 없이 단위·회귀 검사로 오류·시간초과·도구 우회·영수증 위변조 경계를 확인한다.
2. Mac에서는 빈 범위 `not_run`과 로컬 mock만 확인한다.
3. 승인된 정상 요청으로 실제 출발지·pfSense 경유·로그 수집을 확인한 뒤 정찰부터 제한적으로 연다.
4. Windows VM에서는 Python·nmap·`taskkill` 트리 종료와 동일한 프로필을 별도로 검증한다.

## 5. 현재 보류와 성공 기준

- 대상 주소, 계정, 포트, 업로드 파일, CVE 재현 입력값, 시간 한도, 복구 절차는 아직 고정하지 않는다.
- 예시 nmap/sqlmap 도구는 비활성·미연결 상태이며, 승인 목록이 비어 있으면 `not_run`이어야 한다.
- sqlmap은 현재 Mac 실행 이미지에 없다. 자동 설치하지 않는다.
- 현재의 사용자 정의 도구는 목표 완료를 스스로 증명할 수 없다. 단계 B의 서버 측 실행·프로필·독립 증거 연결이 검증되기 전까지 이 경계를 변경하지 않는다.

1차 성공 기준은 실제 공격 성공이 아니라, 하나의 도구 호출에 대해 **프로필/도구 정의/입력 지문/서버 종료 상태/원본 결과/독립 로그 대조 항목**을 빠짐없이 남길 수 있는 상태다.

## 6. 이번 소스 검증 범위

- 오프라인 단위 검증: 실행 영수증, 실패·timeout·프로세스 정리, 기존 목표 근거 차단, 프로필 allowlist, draft fail-closed, profile JSON 형식 검증을 통과했다.
- DB CRUD·삭제 cascade 통합 검사는 새 schema를 실제 Mac DB에 적용해야 하므로 이번에는 실행하지 않았다.
- Docker 이미지 재빌드·기존 ARTEX 서비스 재시작·도구 활성화·웹 대상 요청·스캔은 모두 수행하지 않았다.
